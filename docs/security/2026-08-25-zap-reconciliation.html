Absence of Anti-CSRF Tokens

Medium 10202 · Systemic Not a defect

/login · /request · /sprintsight-coming-soon/intro/

What ZAP flagged

No anti-CSRF token was found in the HTML of these submission forms. ZAP looks for a hidden token field and reports its absence as a Medium risk.

What we found

The hub does not defend CSRF with tokens. It uses an Origin-header guard (hub/middleware/csrf.js), mounted in the app shell above every route, which ZAP has no way to observe from the page source.

It fails closed: a state-changing request carrying neither Origin nor Sec-Fetch-Site is refused, and Origin: null is refused with everything else off the allow-list. The allow-list is derived from the declared public origin, never computed from the request. The four /api/* routes are exempt by path — they are server-to-server calls with a Bearer key and no cookie.

Evidence The scan proves the guard rather than the token. 1,725 of ZAP's 5,209 responses were 403 — the guard refusing its forged requests. No token scheme would have produced better evidence than the scanner's own tally.
Open Two state-changing GET routes sit outside the guard, because safe methods pass through untouched: GET /logout and GET /launch/:app. Both are recorded deliberately rather than closed — closing them means converting the routes to POST and reworking the magic-link redirect chain. ZAP did not flag them; we are naming them because a report that only lists what the scanner found is not an honest one.

CSP: Failure to Define Directive with No Fallback

Medium 10055 · Systemic Fixed

/css · /fonts · /illos · /img · /sitemap.xml

What ZAP flagged

These responses carried Content-Security-Policy: default-src 'none'. Because frame-ancestors and form-action do not fall back to default-src, ZAP reports them as undefined.

What we found

This is the one alert that was live and real. The four directory paths are answered by express.static, which redirects /img to /img/ and writes its own CSP over the one the app shell had already set (serve-static/index.js:203).

Fixed by turning that redirect off. hub/public/ has no directory index, so the 301 only ever led to a 404 anyway; the path now falls through to the branded 404 under the hub's full policy. The /sitemap.xml instance was a 404 captured before the sitemap shipped, and now returns 200.

Verified /img, /fonts, /css and /illos now return 404 under the full hub CSP — no redirect, no Location, no default-src 'none'. Real assets still serve 200. Shipped in e89180d, pinned by a regression test in hub/tests/not-found.test.js that asserts the status before the header.
Honest This repaired no vulnerability. X-Frame-Options: DENY came from our own middleware and survived the overwrite, and a 301 body is never rendered. The fix closes the alert, removes a pointless hop, and makes header behaviour uniform — nothing more.

CSP: style-src unsafe-inline

Medium 10055 · Systemic Fixed before review

/login · /request · /terms

What ZAP flagged

The policy permitted style-src 'self' 'unsafe-inline', which weakens CSP as a defence against injected styling and some data-exfiltration techniques.

What we found

Correct at 10:22 and already fixed by the time the report was generated. Thirty-two inline style attributes were removed from the hub's views and replaced with classes, which let 'unsafe-inline' come out of the policy entirely.

Verified /login, /request and /terms all return style-src 'self' on production, with no 'unsafe-inline'. Shipped in 1423cbb.

Content Security Policy (CSP) Header Not Set

Medium 10038 · 2 instances Fixed before review

/sprintsight-coming-soon/intro/ (both instances)

What ZAP flagged

The SprintSight coming-soon page returned no CSP header at all.

What we found

A real gap, with an instructive cause. That page is static and served by an Apache Alias sitting above a ProxyPass … ! carve-out. The carve-out is what makes the page reachable — and it also removes the request from the hub entirely, so the security-headers middleware never ran on it.

No test in the repository could see this: they all exercise the hub, and Apache is not the hub. Fixed by a <Directory> block on the vhost setting all six headers, including a CSP that matches the hub's byte for byte except for a sha256 hash in place of 'unsafe-inline'.

Verified Live headers confirmed on the page and its assets, and the pinned hash still matches the page's <noscript> block. Shipped in 06ce3cb at 12:23 — two hours after ZAP's capture. Guarded by five tests in marketing/tests/promo-security-headers.test.mjs, which recompute the hash from the file, plus seven probes in the production smoke check.

Missing Anti-clickjacking Header

Medium 10020 · 2 instances Fixed before review

/sprintsight-coming-soon/intro/ (both instances)

What ZAP flagged

No X-Frame-Options and no CSP frame-ancestors on the promo page, leaving it framable by a third-party site.

What we found

Same root cause as the alert above — the Apache Alias bypassing the hub's middleware — and closed by the same <Directory> block, which sets X-Frame-Options: DENY and frame-ancestors 'none' together.

Verified Both headers confirmed live on the page and its assets. Shipped in 06ce3cb.

Strict-Transport-Security Header Not Set

Low 10035 · Systemic Fixed before review

/sprintsight-coming-soon/intro/ and its assets — sight.css, the three pass illustrations

What ZAP flagged

No HSTS header, so a browser is not instructed to refuse a plaintext connection to the host on a later visit.

What we found

Every flagged URL is under the aliased promo path — the same middleware bypass again. The hub's own responses carried HSTS correctly throughout the scan, which is why no hub URL appears in this alert.

Verified max-age=31536000; includeSubDomains confirmed live on the page and its assets. Shipped in 06ce3cb.

X-Content-Type-Options Header Missing

Low 10021 · Systemic Fixed before review

/sprintsight-coming-soon/intro/ and its assets

What ZAP flagged

No nosniff, so a browser may MIME-sniff a response and treat it as a type the server did not declare.

What we found

Same aliased path, same bypass, same fix. As with HSTS, the absence of any hub URL in this alert is the useful signal: the middleware was working everywhere it ran.

Verified nosniff confirmed live on the page and its assets. Shipped in 06ce3cb.

Information Disclosure — Sensitive Information in URL

Informational 10024 · 2 instances Fixed before review

/sprintsight-coming-soon/intro/?email=zaproxy%40example.com

What ZAP flagged

An email address appearing in the query string of a request URL.

What we found

Real, and rated too low by the scanner. The promo page's notify form had no method, so it defaulted to GET. With JavaScript enabled the handler intercepts the submit and nothing leaves the browser — but a visitor without JavaScript would have put their address into the URL, and from there into Apache's access log and their own browser history.

Fixed by declaring method="post", so the no-JS fallback cannot leak the address into either log.

Verified The live form is method="post". Shipped in f84d94e.

Information Disclosure — Suspicious Comments

Informational 10027 · 18 instances Not a defect — acted on

/sprintsight-coming-soon/intro/ (14) · /js/confirm-modal.js · /js/consent-banner.js · /js/ga.js · /js/oscilloscope.js

What ZAP flagged

Source comments matching its suspicious-word list. The words it actually matched were FROM, USER, WHERE and LATER, in ordinary English sentences. As a security finding this is a false positive — the four hub JavaScript files disclose nothing.

What we found

The rule was wrong but it pointed at something true. Fourteen of the eighteen instances were the promo page, whose comments shipped its build-spec commentary to every visitor: internal document paths, and a note that the eval scorecard carries target figures rather than measured results.

Those rules are binding and stay binding, so they were moved rather than deleted — into marketing/docs/sprintsight-promo-EDITING.md, which sits outside public/ and is unreachable through the Alias. Each of the three files keeps a one-line pointer to it. Bare section marks stay: they are useful with the spec open and say nothing without it.

Verified Zero matches for any internal document reference in the live page; the editing doc returns 404 over HTTP. Nothing visible on the page changed, and the pinned CSP hash still matches. Shipped in 8b39869.
Honest This is disclosure hygiene, not a security fix. Nothing in those comments was a credential or a live internal address.

What ZAP flagged

What we found

Re-examine Cache-control Directives

Informational 10015 · Systemic Not a defect

/license · /login · /request · /robots.txt · /terms

What ZAP flagged

These responses do not forbid caching, so a shared or browser cache may store and later re-serve them.

What we found

Every URL in this alert is a public, unauthenticated page carrying no personal data — the licence, the terms, the sign-in form, the registration form and robots.txt. Caching them is correct behaviour, and suppressing it would cost performance for no benefit.

The authenticated surface is handled separately and was not what ZAP reached: authenticated responses carry no-store, and the production smoke check probes that the signed-out redirect from /dashboard carries it too.

Note The no-store work (6c869a4) cleared none of the five instances in this alert and never could — they are different pages. Recorded so this alert is not mistaken for one that a past change was supposed to close.

What shipped

All five commits are on main and deployed to production. Production was fast-forwarded to 77821ae, the hub restarted, and the smoke check passed 29 of 29 probes.

What this scan could not tell us

A clean result is only as wide as the scan that produced it. Four limits are worth carrying into the next one.

  • It ran signed out. The report records No Authentication Statistics Found: every page behind sign-in was probed only as an anonymous visitor. The dashboard, the admin console and the company console were never seen as a logged-in user, so the absence of findings there is absence of testing, not evidence of safety.
  • It is a snapshot of the morning. Six of eleven alerts were already closed when the report was written. Any future scan should be read against the deploy log before any of it is treated as current.
  • The spider may not have reached everything. ZAP's own Modern Web Application alert says links revealed by JavaScript can be missed.
  • Two state-changing GET routes were never exercised. GET /logout and GET /launch/:app sit outside the CSRF guard by design. ZAP did not flag them because it does not know they change state.
